# 上下文压缩算法

对照 ChatDesk、DeepSeek Harness、pi-mono 如何在窗口快满时压缩**发给模型的 prompt**。
用户可见的完整记录通常仍在；被精简的是下一轮模型实际读到的那份上下文。

三家做的是同一件事：**旧工作折成摘要，最近工作原文留下**。差别在何时动手、从哪切开、摘要放哪、压完仍超限怎么办。

## 对照

| | ChatDesk | DeepSeek Harness | pi-mono |
|---|---|---|---|
| 思路 | 写一份检查点塞进 system，对话只留最近几条 | 先削过长工具结果；再把最旧的前缀换成一条检查点用户消息 | 从尾巴按 token 预算原文保留，更早的折成结构化摘要 |
| 何时压 | 每步发送前，用量超过窗口 75%（上限 750K） | 下一步之前（压力）；请求被拒之后（溢出）；或手动 `/compact` | 一轮结束或下一轮发送前；用量超过「窗口 − 预留」；或提供商已拒 |
| 切点 | 按**条数**：删旧 reasoning / 旧工具，再留大约 6 条 | 按**前缀**：从头压到尾巴预算处；不保证整轮完整 | 按**尾巴预算**：尽量整轮保留，单轮太大才拆开 |
| 摘要放哪 | system 里的检查点块；计划原文另附 | 表面上一条用户检查点，替换被压掉的节点 | 会话树追加一个压缩节点，重建时变成一条合成用户消息 |
| 历史记录 | 不改 Session Store | 日志只追加；表面用替换表达「模型看见什么」 | 日志只追加；磁盘树仍可走回压缩前 |
| 压完仍超 | 停止 run | 压力路径可再压一轮；溢出路径可重试一次请求 | 溢出：丢掉失败回复、压一次再 continue；阈值触发不重试本轮 |
| 调模型 | 是，写检查点 | 是，写摘要；若只靠削工具结果就够，可以不写摘要 | 是，写历史摘要；拆轮时再并行写一份前缀摘要 |

共同底线：不要把「助手的工具调用」和「对应的工具结果」从中间切开。

## 同一段对话，三种切法

下面这段会话在三家眼里会被切成不同形状。数字只为示意，不是真实 token。

```
[0] 用户：登录过期后刷新会丢购物车
[1] 助手：先读 auth 和 cart          + 两大份文件原文
[2] 助手：改了 refreshSession        + patch 成功
[3] 用户：跑测试
[4] 助手：跑 cart.spec               + 很长的失败日志
[5] 助手：失败是 cookie 没带回       ← 当前叶子
```

**ChatDesk** 先写检查点（目标、已读文件、已做修改、下一步），塞进 system；对话里只留最近几条，更早的大段工具原文直接丢掉。

```
system:  …原有指令…
          <检查点> 目标=修刷新丢购物车；已改 refreshSession；测试仍失败 … </检查点>
          <计划全文，若有>

发给模型的对话：  [3] 跑测试  [4] 测试日志  [5] cookie 判断
                  （[0][1][2] 只活在检查点里）
```

**DeepSeek** 往往先把 `[1]` `[4]` 里过长的工具正文砍成「头 + 省略 + 尾」。若还超，再把最旧的一段换成一条检查点用户消息，尾巴按窗口比例留下。

```
先削工具结果：  [1] 文件原文  →  前 4K 字 + 「省略了 N 字」 + 后 1K 字

再换前缀：      [检查点用户消息，替换 0–3]
                [4] 已削过的测试日志
                [5] cookie 判断
```

**pi-mono** 从 `[5]` 往回加，加满「最近约 20K token」就停。切口尽量落在用户发言上；如果 `[3]–[5]` 单轮就超预算，会把这一轮前半段另做一份短摘要。

```
保留原文：      [4] 测试日志  [5] cookie 判断

合成用户消息：  历史摘要（[0][1][2] 的目标/决策/文件）
                + 若拆轮：这一轮前半段发生了什么
```

同一份工作，ChatDesk 用「少条数 + system 检查点」换空间；DeepSeek 用「削工具 + 换掉旧前缀」；pi-mono 用「保尾巴 token + 摘要当作用户话」。

## ChatDesk：检查点进 system，尾巴按条数留

面向**当前这一次 run 的后续步骤**。判断发生在每一步真正请求模型之前。压缩不改用户看到的聊天记录。

### 思路

1. 用量用偏大的字符估算，并和上一轮供应商返回的真实输入 token 取较大值，避免「估少了迟迟不压」。
2. 超过窗口 75%（再封顶 750K）就动手。余量留给 system、工具定义、输出和估算误差。
3. 另调一次模型，按固定小标题写一份**只含事实**的检查点（目标、约束、已确认事实、查过的文件、决策、未决问题、下一步）。已有检查点和当前计划一并喂进去；计划是权威状态，检查点不得改写它。
4. 对话侧删掉隐藏推理、删掉「最后几条之前」的工具内容，再只留大约 6 条。切点如果落在一条孤零零的工具结果上，就向前扩，保证调用和结果成对。
5. 检查点放进 system，而不是塞回对话。下一轮模型看到的是「人设 + 检查点 + 计划 + 最近几条」。
6. 同一 run 里检查点会留下来，下次压缩是**更新**它，不是从零重写。压完仍超阈值，或检查点写不出来，就结束这次 run，不带着超限上下文继续。

```
超限前：  system + 很长的工具来回
超限后：  system + 检查点 + 计划  |  最近约 6 条原文
```

### 例子：多步改文件之后

Agent 已经读过 8 个文件、打过 3 次补丁。第 9 步发送前估算超过 75%。

- 检查点会记下：要修刷新丢购物车、`refreshSession` 已改、测试仍红、下一步是看 cookie。
- 发给模型的对话可能只剩「跑测试」这一轮的原文；更早那 8 次 `read_file` 的全文不再出现。
- 用户回看聊天，那些工具卡片都还在。

若检查点生成失败，或剪完仍超 75%，run 以失败收尾，而不是再赌一轮主模型。

产品侧提示和弹窗见 [`docs/chat-context-compaction.md`](./chat-context-compaction.md)。工具输出截断、重复读文件去重、跨会话记忆整理，都不是这套 run 内压缩。

## DeepSeek Harness：先削工具结果，再换掉最旧前缀

压缩是可选能力：没装这套后端，窗口压力不会改写历史。装上之后，它改的是模型看见的**表面**；底层日志仍追加，回放能还原压缩前的节点。

### 思路

先问「现在这份请求贵不贵」，再决定是只砍工具正文，还是连旧对话一起换成检查点。

1. **压力**：下一步开始前计量。超过窗口约 80% 才压；尾巴大约留窗口的 16%，给下一轮回复留空。
2. **溢出**：提供商已经以上下文超限拒了。不再看阈值，尽量多压前缀，只留下最新那一个不可再拆的单元，然后允许重试这次请求。
3. **手动**：会话空闲时 `/compact`，同样尽量多压，不自动重试对话。

无论哪条路，只要动手，往往先跑一遍**工具结果修剪**：超长文本留开头和结尾，中间写成省略了多少。许多次超限其实是某次 `read` / 测试日志太大；砍完再量，压力路径若已经掉到阈值下，就不必再写摘要。

还超的话，从**最旧的节点往新处压**。从尾巴往回加到「该留的 token」为止，切口必须落在「没有未闭合的工具调用」的边界上。被压掉的前缀交给摘要模型，换成**一条用户检查点消息**，替换那些节点。摘要必须比被替换的内容更短，否则视为失败，表面不动。

压力路径成功一次后若仍超阈值，可以再压一轮。溢出路径看表面有没有真正往前推进（包括「只修剪了工具结果」）；推进了才重试请求，默认最多一次。

```
压力：   量一下 → 超了再削工具 → 还超再换前缀 → 仍超可再来一轮
溢出：   已失败 → 削工具 → 尽量换前缀 → 有进展则重试这次请求
手动：   空闲 → 不削？按实现是不跑修剪，直接尽量换前缀
```

（手动路径不跑修剪：修剪挂在「已经判定需要自动压」之后。）

### 例子：一次超长 read 撑满窗口

窗口 100K，阈值约 80K，尾巴预算约 16K。表面是：

```
[0] 用户：解释这个仓库
[1] 助手：读 README + 五个源文件     ← 工具正文合计 90K
[2] 助手：开始画模块关系             ← 最新一条
```

压力触发后先把 `[1]` 的工具正文砍到「头 4K + 省略 + 尾 1K」量级。若总量掉到 80K 以下，到此为止，`[0][2]` 原样保留。

若仍超，再把 `[0][1]` 换成一条检查点（「这是个购物车服务，入口在 …」），表面变成：

```
[检查点用户消息]
[2] 开始画模块关系
```

若 `[2]` 还是一次未完成的工具调用（有 call 无 result），切口不能落在这对中间，会拒绝压缩，等这对闭合。

摘要调用会尽量复用当前会话的 system / 工具 / 被压前缀，只在最后追加压缩指令，便于前缀缓存。思考过程和工具调用不会写进检查点，避免泄漏推理或留下没有结果的调用。

系统提示、工具 schema、单条无法再拆的节点、以及从未成功发过路由请求的会话，这套算法救不了。

## pi-mono：从尾巴量预算，摘要当作用户消息

面向**整段会话树**，不是单次 run 的临时上下文。压缩对 prompt 有损，对存储无损：只追加压缩节点，重建 prompt 时不再整段回放更早的原文。

### 思路

1. 触发看供应商 usage（或「最后一次 usage + 其后字符估算」）。阈值是「窗口减去预留给下一轮回复的空间」，默认预留约 16K。窗口 100K 时，用量过约 84K 就压。
2. 切点不能用 usage：usage 是整段累计，分不出该丢哪条。从最新消息用字符/4 往回加，加满「最近约 20K」停在合法切口。字符/4 偏大，所以真正留下的尾巴往往略小于标称值。
3. 合法切口是用户 / 助手 / 已有摘要；**不能是工具结果**。带工具调用的助手消息可以切——它后面的结果会跟进保留区。
4. 尽量切在一轮的用户起点上。只有这一轮本身就大于保留预算，才拆轮：前半轮另做短摘要，后半轮原文留下。
5. 待摘要内容先序列化成一篇带标签的文档（不是继续聊天），工具结果截到约 2K 字。模型按固定小标题写 Goal / 进度 / 决策 / 下一步等。后一次压缩带上上一份摘要做更新，并累积读过、改过的文件列表。
6. 重建时只认路径上**最新一份**摘要 + `firstKept` 之后的原文。更早的摘要不会叠成第二、第三条。

两条自动路径：

- **溢出**（提供商已拒，或静默发现输入已大于窗口）：从内存丢掉这条失败回复，压缩后 continue **一次**。
- **阈值**（快满但本轮还没被拒）：压缩后不重试本轮；若已有排队的跟进消息，再 continue，避免队列卡住。

刚压完会用压缩时间戳挡住「压缩前的旧 usage」，否则会立刻再压一次。

### 例子：整轮能留下

```
更早 40 轮调研  |  用户：修测试  |  助手+三次工具  |  助手：还差断言
                 ^ 切口（用户起点）
```

尾巴 token 够盖住「修测试」这一整轮 → 历史 40 轮进摘要，这一轮原文全留。

发给模型：

```
system
用户：以下是压缩摘要 …（含读过/改过的文件列表）
用户：修测试
助手：… 三次工具原文 …
助手：还差断言
```

### 例子：单轮太大，只好拆开

「修测试」这一轮里已经有三次巨大的测试日志，单轮就超过 20K。

```
[更早轮次 | 用户：修测试 | 工具×2 | 工具×1 | 助手：还差断言]
           ^ 回合起点              ^ 保留起点
           （前半轮进短摘要）      （原文留下）
```

两份摘要并行：一份更新整段历史，一份只解释「这一轮前半段跑过哪些测试、失败长什么样」。合并后再追加压缩节点。

### 和「换分支」不是一回事

切换会话树、丢掉一条探索路径时，也可以把那条路径折成摘要注入当前对话。那是为了**把放弃的工作带回来**，不是因为窗口满了。预算、是否序列化工具结果、产出的节点类型都不同。

## 选型时真正分叉的几件事

**摘要放 system 还是放用户消息。**  
ChatDesk 把检查点当成给后续步骤的指令，对话里只剩短尾巴。DeepSeek / pi-mono 把摘要当成对话里的一条用户话，后面仍是正常多轮。前者实现简单、和「当前 run」绑定；后者更像会话的永久折点。

**按条数留，还是按 token 留。**  
ChatDesk 的 6 条在工具原文很大时可能仍然很贵，所以必须先删旧工具体。DeepSeek / pi-mono 用 token 预算约束尾巴；DeepSeek 还多一刀「先把单条工具结果砍短」。

**从头换前缀，还是从尾向量预算。**  
DeepSeek 总是压最旧的那段（最近的工作更可能还要用）。pi-mono 从新往旧量，并尽量不切断一轮中间。ChatDesk 几乎不处理「一轮」的概念。

**溢出后赌不赌下一轮主模型。**  
ChatDesk 不赌。DeepSeek 和 pi-mono 都允许「压完再试一次」，但都有次数帽，避免拒→压→再拒的死循环。

**多次压缩会不会越压越空。**  
三家都选择「更新上一份摘要」，而不是每次从会话开头重读。pi-mono 和 DeepSeek 把这一点做进存储（最新检查点覆盖旧前缀的可见性）；ChatDesk 把上一份检查点字符串再喂给下一次检查点模型。
